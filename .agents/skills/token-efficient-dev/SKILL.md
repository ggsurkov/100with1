# Экономия токенов при работе с 100with1

Проект целиком — ~7500 строк. Прочитать его весь можно, но не нужно: 90 % задач
затрагивают 1–3 файла. Ниже — как их найти, не сжигая контекст.

## 1. Не сканируй проект вслепую

Сначала — скилл `project-map`: там полный инвентарь файлов с размерами и таблица
«задача → что читать». Только если карта не дала ответа, переходи к `Grep`.

Порядок дешевизны: **карта → `Grep` с `output_mode: "files_with_matches"` → `Grep` с `-n` и
`-C 3` → чтение куска файла → чтение файла целиком**. Не начинай с последнего.

## 2. Читай куски, а не файлы целиком

Крупные файлы, которые почти никогда не нужны целиком:

| Файл | Строк |
|---|---|
| `client/src/pages/GameEdit.tsx` | 481 |
| `client/src/pages/RoundCheck.module.scss` | 464 |
| `client/src/pages/GameEdit.module.scss` | 401 |
| `client/src/pages/RoundCheck.tsx` | 385 |
| `server/src/routes/api.ts` | 376 |
| `client/src/pages/GameRounds.module.scss` | 352 |

Для них: `Grep` по имени функции/класса → `Read` с `offset`/`limit` вокруг найденной строки.
`.module.scss` вообще не читай целиком — ищи конкретный класс.

## 3. Не запрашивай Git

Git-команды в этом репозитории **запрещены** (`git status`, `diff`, `log`, `add`, `commit`,
`push`, `checkout`, `branch`). Версионированием занимается человек вручную.
Не проси показать диф — он ничего не даёт по сравнению с чтением самого файла,
но стоит контекста. По завершении задачи просто напиши краткое резюме правок.

## 4. Дешёвая верификация

Единственная проверка в проекте — типы:

```bash
cd server && npx tsc --noEmit    # правил только бэкенд
cd client && npx tsc --noEmit    # правил только фронтенд
```

- Гоняй проверку **только той части**, которую менял, и **один раз** в конце,
  а не после каждой правки.
- Автотестов и линтера нет — не выдумывай `npm test` и не предлагай их поставить без запроса.
- Два deprecation-warning в `client/tsconfig.json` — известный шум, не баг, не чини.
- Не перезапускай `npm start`, если он уже поднят: сервер под `nodemon`, клиент под Vite —
  оба перечитывают изменения сами.

## 5. Не перечитывай то, что уже знаешь

- После `Edit`/`Write` **не читай файл обратно** для проверки — правка либо применилась,
  либо вернула ошибку.
- Не пересказывай пользователю содержимое файла, который он и так видит.
- Не выводи большие блоки кода в ответе: назови `файл:строка` — этого достаточно.
- Не повторяй в ответе то, что уже сказал в предыдущем сообщении сессии.

## 6. Сужай задачу до правки

Прежде чем читать код, определи по формулировке задачи, к какой группе экранов она относится
(см. `project-map`): **админка**, **экран ведущего**, **телефон капитана**, **публичное**.
Это сразу отсекает 3/4 файлов. Если из формулировки это не следует — задай **один** уточняющий
вопрос (какой экран / какой роут), а не читай всё подряд «на всякий случай».

## 7. Правки — точечные

- `Edit` с минимальным уникальным контекстом вместо перезаписи файла через `Write`.
- Не переформатируй соседний код, не трогай кавычки, отступы и порядок импортов
  за пределами правки — это раздувает и правку, и последующее ревью.
- Не делай попутный рефакторинг, которого не просили. Исключение — дубли из скилла
  `frontend-react`: их устраняют **в том файле, который и так правишь**.

## 8. Не поднимай решённые вопросы

Это уже решено, обсуждать заново не нужно (и не нужно тратить на это токены):

- Tailwind не используется и не будет.
- Стили — только SCSS Modules.
- Файлы на диск сервера не пишутся (Render, эфемерная ФС) — только Cloudinary.
- Refresh-токенов нет, JWT живёт 1 день.
- Git делает человек.
- Сид-админ `admin@admin.com` / `admin` — известный долг, не «чини» его в рамках чужой задачи.

## 9. Формат ответа

- Резюме правок: список `файл — что изменено`, 1–2 строки на файл.
- Без преамбул («Сейчас я...»), без пересказа плана, который уже выполнен.
- Проблему, найденную по пути, но не входящую в задачу — назови одной строкой и не чини молча.
